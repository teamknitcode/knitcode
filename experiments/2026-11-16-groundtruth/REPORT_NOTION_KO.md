# 정답 호출 그래프 기반 정적·동적 결합 실험

> **동적 분석이 호출 누락을 보완하는 사례는 확인했지만, 이번 범위에서 F1 향상은 확인하지 못했다. 호출 중심·전체 추적의 호출 그래프 점수는 같았다.**

실험일: 2026-11-16

## 1. 확인하려는 것

정적 분석의 호출 후보를 실제 실행으로 보강했을 때 **정답 그래프 대비 정밀도·재현율·F1이 개선되는지**, 그리고 그 개선에 드는 비용을 비교한다.

- 정밀도: 예측한 호출 중 정답인 비율
- 재현율: 정답 호출 중 찾아낸 비율
- F1: 정밀도와 재현율을 함께 평가

호출 지점을 내부·외부·미해결로 분류한 비율과 정답 호출을 찾은 비율은 다르다. 분류율이 100%여도 호출 그래프가 정확하다는 뜻은 아니다.

## 2. 대상과 비교 방법

[공식 PyCG 평가 자료](https://github.com/vitsalis/pycg-evaluation)의 사람이 만든 정답과 고정 소스를 사용했다. 정적 입력 파일 범위는 기존 KnitCode PyCG 평가 어댑터를 그대로 따른다.

| 프로젝트 | 분석 범위 규모 | 실행한 원본 테스트 |
|---|---:|---|
| autojump | Python 4파일 / 2,945줄 | unit: 23 통과·5 skip·4 xfail |
| asciinema | Python 24파일 / 1,553줄 | config·asciicast: 25 통과 |
| Fabric | Python 20파일 / 2,888줄 | transfer·group·config: 66 통과 |

줄 수는 주석·빈 줄을 포함한다. 실제 오픈소스 macro-benchmark이지만 대형 서비스 규모를 검증한 것은 아니다.

동일 테스트에 대해 **일반 실행 / 호출 중심 / 전체 추적을 각 3회** 수행했다. 정적 분석은 실행당 반복하지 않고 한 번 수행했으며, 추적 모드 실행 순서는 회차마다 바꿨다.

결합 결과는 **정적 그래프 ∪ 소스 검증을 통과한 프로젝트 내부 실행 호출**이다. 정답은 채점에만 사용하고, 정답에 없는 추가 호출도 제거하지 않았다. 외부 호출 관찰·람다 등 연결되지 않은 실행 범위는 자동으로 추가하지 않았다.

## 3. 정확도 결과

기존 평가와 비교할 수 있도록 **공식 채점 함수의 점수**를 표시한다. 동적 보강은 두 가지 모드로 비교한다.

- **호출 중심:** 호출 관계·이벤트 수·인자 및 반환 타입 수집
- **전체 추적:** 호출 중심 정보에 줄·분기·변수 접근 수집 추가

| 프로젝트 | 방법 | 정밀도 | 재현율 | F1 | 새 TP / 새 FP | 분석 총시간 |
|---|---|---:|---:|---:|---:|---:|
| autojump | 정적 단독 | 96.46% | 71.14% | 81.89% | — | 0.597초 |
| autojump | 정적 + 호출 중심 | 96.46% | 71.14% | 81.89% | 0 / 0 | 1.303초 |
| autojump | 정적 + 전체 추적 | 96.46% | 71.14% | 81.89% | 0 / 0 | 1.414초 |
| asciinema | 정적 단독 | 92.06% | 75.07% | 82.70% | — | 0.320초 |
| asciinema | 정적 + 호출 중심 | 92.06% | 75.07% | 82.70% | 0 / 0 | 1.120초 |
| asciinema | 정적 + 전체 추적 | 92.06% | 75.07% | 82.70% | 0 / 0 | 1.277초 |
| Fabric | 정적 단독 | 92.18% | 58.79% | 71.79% | — | 0.361초 |
| Fabric | 정적 + 호출 중심 | 91.09% | 59.06% | 71.66% | 1 / 3 | 1.786초 |
| Fabric | 정적 + 전체 추적 | 91.09% | 59.06% | 71.66% | 1 / 3 | 2.192초 |

분석 총시간은 정적 분석 1회 시간 + 각 회차의 (추적 실행 + 사후 비교) 중앙값이다. 정적 시간은 1회 측정치이며, 결합 시간은 이 값을 재사용한 계산값이다. 일반 실행 시간은 추적 실행에 이미 포함되므로 다시 더하지 않았다.

모든 프로젝트에서 결합 호출 집합은 모드·반복 간 동일했다. autojump와 asciinema는 이번 테스트에서 관찰하고 정적 노드에 연결한 호출이 이미 정적 결과에 있었다.

공식 정답에는 중복 항목이 있다(autojump 537항목/535고유쌍, asciinema 341항목/340고유쌍). 위 표는 공식 점수를 보존하고, 원본 JSON에는 고유쌍 TP·FP·FN으로 계산한 점수도 함께 저장했다. 두 기준 모두 이번 실험의 개선 여부 판단은 같다.

### Fabric에서 추가된 관계

| 호출자 → 호출 대상 | 공식 정답 판정 |
|---|---|
| `connection.opens → Connection.sftp` | TP |
| `connection.opens → Connection.open` | FP |
| `Group.__init__ → Connection.__init__` | FP |
| `SerialGroup.run → Connection.__hash__` | FP |

FP는 **공식 정답에 없는 관계**라는 뜻이다. 첫 번째 FP는 소스에 직접 호출이 있고, 나머지도 `map`의 생성자 호출과 딕셔너리 키의 해시 호출로 설명될 수 있다. 정답의 누락·암묵 호출 포함 정책·테스트 바꿔치기 여부를 추가 검토해야 한다. 이번 점수에서는 정답을 수정하거나 FP를 제외하지 않았다.

## 4. 실행 비용

아래는 전체 명령 시간의 중앙값이다. 추적 시간은 프로세스 시작·초기 소스 스캔·실행·기록 저장을 포함하며 정적 분석과 사후 비교는 별도다.

| 프로젝트 | 정적 분석 1회 | 일반 실행 | 호출 중심 | 전체 추적 |
|---|---:|---:|---:|---:|
| autojump | 0.597초 | 0.134초 | 0.616초 | 0.725초 |
| asciinema | 0.320초 | 0.170초 | 0.727초 | 0.870초 |
| Fabric | 0.361초 | 0.285초 | 1.349초 | 1.715초 |

사후 비교 중앙값은 약 0.077~0.116초였다. 최초 결합 분석 비용은 **정적 분석 + 추적 실행 + 사후 비교**를 합쳐 해석해야 한다.

전체 추적은 호출 중심보다 시간이 약 **18~27% 더 들었지만**, 추가 수집한 변수·분기 정보를 아직 정적 추론에 되먹이지 않아 호출 그래프 점수는 같았다. 이 결과만으로 전체 추적의 잠재적 보완 효과가 없다고 결론 내릴 수는 없다.

## 5. 결과가 유의미한가?

**정확도 개선을 입증한 결과로는 부족하지만, 구현 방향을 결정하는 탐색 실험으로는 의미가 있다.**

| 판단 대상 | 현재 결론 |
|---|---|
| 동적 보강으로 전체 정확도가 좋아졌는가? | 입증하지 못함. 두 프로젝트는 변화 없고 Fabric F1은 소폭 하락 |
| 실제 누락을 보완할 수 있는가? | Fabric에서 공식 정답 호출 1개 추가 확인. 일반적 효과를 주장하기에는 적음 |
| 어떤 추적을 기본으로 쓸 것인가? | 현재 호출 합집합 방식에서는 호출 중심이 같은 점수를 더 낮은 비용으로 제공 |
| 전체 추적이 불필요한가? | 결론 불가. 추가 수집한 분기·변수 정보를 정적 추론에 아직 활용하지 않음 |

3회 반복은 실행 비용의 변동을 줄이기 위한 것이며, 서로 다른 테스트·프로젝트 표본을 늘린 것이 아니다. 통계적 유의성 검정은 수행하지 않았다. 선택 테스트의 제한과 외부·미매핑 호출 제외 때문에 전체 동적 보강의 효과를 일반화할 수 없다.

## 6. 다음 작업

- **단순 합집합만으로 정확도 향상을 보장하지 못한다.** Fabric은 재현율 +0.26%p, F1 -0.14%p였다.
- **기본 수집 후보는 호출 중심을 유지한다.** 동일 호출 보완 결과에서 비용이 더 낮았다.
- **다음은 누락 원인과 실행 범위 분석이다.** 정적 미해결 지점이 실제 실행됐는지, 누락이 내부·외부·동적 생성·매핑 실패 중 어디에 해당하는지 나눈다.
- 전체 추적의 타입·분기 정보를 정적 추론에 반영하는 실험은 별도 결합 규칙과 평가가 필요하다.
- 관찰하지 못한 정적 후보는 삭제하지 않는다. 테스트가 커버하지 않은 경로를 오류로 처리하지 않는다.

## 검증 범위와 재현

- macOS ARM64 / Python 3.11.8. 구형 테스트 의존성 때문에 이전 Requests 실험의 Python 3.12와 다르며, 시간 수치를 직접 비교하지 않는다.
- Fabric은 pytest-relaxed의 pytest 7 수집 오류로 별도 pytest 4.6.11 환경과 `--assert=plain`을 사용했다. connection 모듈은 일반 실행부터 2개 실패해, 전체 모듈을 정확도 측정 전에 제외했다. 테스트 소스는 수정하지 않았다.
- 3개 프로젝트에서 27회 명령 모두 정상 종료, 추적 기록은 모두 `complete=true`였다. 이는 모든 경로를 실행했다는 뜻이 아니다.
- 동적 호출 집합은 실행된 경로와 매핑 가능한 범위에 한정된다. 외부 호출 관찰은 현재 결합에 사용하지 않아 외부 호출 누락을 보완하지 못한다.
- 도구 버전은 `5d5c63d` + 이전 실험의 가상환경 경로 수정이며, 실제 수집 소스 해시·프로젝트 커밋·의존성은 결과 메타데이터에 저장했다.

```bash
/path/to/python3.11-venv/bin/python experiments/2026-11-16-groundtruth/hybrid_evaluation.py \
  --tool /path/to/corrected-pr-worktree --benchmark /path/to/pycg-evaluation \
  --python /path/to/python3.11-venv/bin/python \
  --out out/groundtruth-hybrid --projects autojump asciinema --rounds 3
```

Fabric은 별도 호환 환경으로 `--projects fabric --legacy-pytest`를 사용한다. 실행에는 macOS `/usr/bin/time -l`이 필요하며, 최대 RSS는 동시 프로세스 메모리의 합계가 아니다.

산출물: `hybrid_evaluation.py`, `results/results.json`, 프로젝트별 반복 측정·추가 호출 목록·로그·환경 메타데이터. 전체 실행 기록과 정적 결과는 로컬 `out/groundtruth-hybrid/`, `out/groundtruth-fabric/`에 보존했다. 원격 반영·병합은 하지 않았다.
