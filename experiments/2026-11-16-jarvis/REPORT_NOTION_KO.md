# Jarvis 후속 데이터셋 — 동적 보조 분석 평가

> **독립적인 후속 데이터셋에서 호출 중심 보강의 F1 향상을 확인했다. 다만 정밀도 손실과 실행 비용이 있어, 관찰 관계를 근거와 함께 제공하는 방향이 적절하다.**

실험일: 2026-11-16 · 도구: PR #4 병합 main `b0eaa8a`

## 1. 대상과 평가 범위

[Jarvis 공식 자료](https://github.com/pythonJaRvis/pythonJaRvis.github.io)의 고정 소스와 `EA.json` 정답을 사용했다. 이전 PyCG macro 프로젝트와 다른 sqlparse·furl을 평가했다.

| 대상 | 앱 Python 소스 | 원본 테스트 실행 범위 |
|---|---|---|
| sqlparse | 21파일 / 3,803줄 | 425 통과·3 xfail |
| furl | 6파일 / 2,104줄 | 75 통과, 기본 실행부터 실패한 2개 제외 |

Jarvis 정답에는 import·클래스 본문·외부 호출도 섞여 있다. 이번 주평가는 **호출자와 호출 대상 모두 앱 소스에 선언된 함수인 관계**로 한정했다. GT와 모든 예측에 같은 조건을 적용했으며, 함수 목록은 GT·분석기 결과와 독립적으로 소스 AST에서 만들었다.

- sqlparse: 원본 EA 612관계 중 함수 간 351관계 평가
- furl: 원본 EA 319관계 중 함수 간 189관계 평가
- 모듈 진입·클래스 본문·외부/내장·람다·소스에 없는 동적 생성 함수는 주평가 범위 밖
- 정답은 채점에만 사용. 추가된 호출을 정답에 맞춰 선택하거나 삭제하지 않음

**Jarvis 논문의 전체 EA 점수를 그대로 재현한 결과가 아니며, 이전 PyCG 표와 절대 점수를 직접 비교하면 안 된다.** 같은 데이터·범위에서 세 방법 간 차이를 비교한다.

## 2. 세 방법 비교

| 프로젝트 | 방법 | 정밀도 | 재현율 | F1 | 새 TP / 새 FP | 분석 총시간 |
|---|---|---:|---:|---:|---:|---:|
| sqlparse | 정적 단독 | 89.52% | 53.56% | 67.02% | — | 0.550초 |
| sqlparse | 정적 + 호출 중심 | 88.17% | 97.72% | 92.70% | 155 / 24 | 6.071초 |
| sqlparse | 정적 + 전체 추적 | 88.17% | 97.72% | 92.70% | 155 / 24 | 38.733초 |
| furl | 정적 단독 | 86.46% | 43.92% | 58.25% | — | 0.329초 |
| furl | 정적 + 호출 중심 | 71.81% | 86.24% | 78.37% | 80 / 51 | 65.676초 |
| furl | 정적 + 전체 추적 | — | — | — | — | 추적 240초 초과 |

정적 분석은 1회 측정했다. 정상 완료한 일반 실행·추적은 각 3회 측정했고 순서를 회차마다 바꿨다. 분석 총시간은 정적 분석 시간 + (추적 실행·저장 + 사후 비교)의 중앙값이다. 일반 실행 시간은 추적 실행에 포함되므로 다시 더하지 않는다.

furl 전체 추적은 첫 실행이 **240초 제한을 초과**해 나머지 반복을 중단했다. 완료 점수나 중앙값을 추정하지 않았으며 호출 중심 결과를 대신 채워 넣지 않았다.

## 3. 정확도 개선의 의미

| 대상 | 호출 중심 보강 효과 |
|---|---|
| sqlparse | 정답 155개 추가, GT 밖 관계 24개 추가. 재현율 +44.16%p, F1 +25.68%p |
| furl | 정답 80개 추가, GT 밖 관계 51개 추가. 재현율 +42.33%p, F1 +20.12%p |

sqlparse에서는 `FilterStack.run`이 실제 사용한 `StatementSplitter.process`, 여러 필터의 `process` 구현체 등 정적 분석이 놓친 대상을 관찰했다. furl에서는 생성자·상속·속성 처리를 거치는 호출을 보강했다.

**실행 관찰은 실제 경로의 증거이며, GT 전체를 대신하지 않는다.** GT 밖 관계는 채점상 FP로 유지했다. 이 중에는 중첩 래퍼·property·특수 메서드 호출도 있어, 정답의 포함 정책이나 매핑 문제인지 추가 검토해야 한다. 미관찰 정적 후보도 삭제하지 않았다.

이번 결과는 두 프로젝트의 고정 테스트에서 **단순 호출 합집합도 누락을 크게 보완할 수 있음**을 보여준다. 그러나 정밀도는 두 프로젝트 모두 내려갔고, 테스트가 실행하지 않은 경로 및 평가 범위 밖 호출까지 개선됐다는 뜻은 아니다.

## 4. 비용과 제품 방향

| 프로젝트 | 일반 실행 | 호출 중심 추적 | 전체 추적 | 호출 중심 최대 RSS | 호출 중심 기록 크기 |
|---|---:|---:|---:|---:|---:|
| sqlparse | 0.378초 | 5.468초 | 38.070초 | 94.5 MiB | 1.43 MiB |
| furl | 2.313초 | 65.310초 | 240초 초과 | 107.4 MiB | 1.46 MiB |

sqlparse는 두 추적 모드의 결합 호출 집합이 3회 반복 모두 같았다. 전체 추적의 변수·분기 정보는 현재 정적 추론에 반영하지 않으므로 호출 중심보다 높은 점수를 만들지 못했다. furl은 전체 추적이 미완료여서 모드 간 정확도 동등성을 판단하지 않는다.

furl 호출 중심 기록에는 약 **900만 건의 프로파일 호출 이벤트**가 있었다. 테스트 개수·코드 줄 수만으로 추적 비용을 예측할 수 없으며, 반복 호출량도 중요하다.

- **기본:** 정적 그래프로 구조와 후보 제공
- **보조:** 사용자가 선택한 테스트를 호출 중심으로 추적해 실행 근거·추가 관계 표시
- **상세:** 변수·분기 정보가 필요한 경우 전체 추적 선택. 실행 시간 제한과 중단 상태 표시

다음 과제는 새 FP의 원인 분류와 호출 중심 수집 비용 최적화다. 같은 GT에 맞춰 규칙을 튜닝한 뒤 같은 데이터만으로 개선을 주장하지 않도록 별도 평가 대상을 유지한다.

## 5. 재현 및 한계

- macOS ARM64 / Python 3.11.8 / pytest 7.4.4
- 공식 artifact 커밋: `8871b86494a1aec0095686ffa543994a7361af88`
- 원본 자료가 명시한 upstream 버전: sqlparse `9f44d54`, furl `7748462`. 실제 평가는 고정 artifact의 소스 snapshot 사용. 파일 해시도 저장
- furl의 제외 테스트: `TestFurl.test_hosts`, `TestFurl.test_netloc`. Python 3.11 `urllib.parse`의 IPv6 검증에서 일반 실행부터 실패. 테스트·앱 소스는 수정하지 않음
- `complete=true`는 수집 정상 종료를 뜻하며 모든 코드 경로 실행을 뜻하지 않음
- 반복은 비용 변동과 결과 일관성 확인용. 통계적 유의성 검정이나 다른 대형 프로젝트로의 일반화는 미실시
- 추적 대상에 테스트 코드도 포함돼 실행 비용에 반영되지만, 테스트 함수에서 출발한 관계는 주평가에서 제외
- 최대 RSS는 macOS `/usr/bin/time -l` 값이며 동시 프로세스 메모리의 합계가 아님

furl 제한 초과 시 최초 실험 실행기가 하위 프로세스까지 종료하지 못해 잔여 worker를 명시적으로 정리했다. 이후 프로세스 그룹 종료·재개 기능을 실험 스크립트에 추가했다. 수집기·점수 규칙은 변경하지 않았으며 완료한 측정은 재사용했다.

```bash
/path/to/venv/bin/python experiments/2026-11-16-jarvis/evaluate.py \
  --tool . --artifact /path/to/pinned-jarvis-artifact \
  --python /path/to/venv/bin/python --out out/jarvis-hybrid --rounds 3
```

산출물: `PROTOCOL_KO.md`, `evaluate.py`, `results/`의 점수·반복 측정·추가 관계·소스 해시·로그. 큰 실행 기록은 로컬 `out/jarvis-hybrid/`에 보존했다. 이번 실험 파일은 PR #4의 수집기 구현과 구분해 별도 실험 자료 PR로 제출한다.
