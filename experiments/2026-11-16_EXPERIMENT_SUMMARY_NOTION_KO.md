# 정적 분석을 보조하는 동적 분석 — 실험 흐름과 결과

**2026-11-16 · KnitCode**

> 정적 분석을 기본으로 유지하면서 실제 호출을 보강한 결과, Jarvis의 두 프로젝트에서 F1 개선을 확인했다. 다만 정밀도 손실과 추적 비용이 있어, 선택한 테스트를 호출 중심으로 추적하는 방식을 우선한다.

## 1. 실험 목적

**동적 분석이 정적 분석의 누락을 얼마나 보완하며, 그 효과에 비해 비용은 적절한가?**

정확도 개선과 함께, 사용자가 정적 호출 후보를 실제 실행 근거와 대조할 수 있는지도 확인한다.

| 비교 방법 | 동작 |
|---|---|
| 정적 단독 | 코드를 실행하지 않고 호출 관계 추론 |
| 정적 + 호출 중심 | `sys.setprofile`로 호출·타입을 관찰해 정적 그래프 보강 |
| 정적 + 전체 추적 | 호출 중심 정보에 줄·분기·변수 접근 수집 추가 |

실행에서 관찰한 호출을 정적 그래프에 **합집합으로 추가**했다. 미관찰 정적 후보는 삭제하지 않았고, 정답에 없는 관찰도 임의로 제외하지 않았다. 전체 추적의 변수·분기 정보는 아직 정적 추론에 반영하지 않았다.

## 2. 진행 흐름

1. **인계 코드 검증·수정** — Python 3.12 opcode 이벤트 누락과 가상환경 실행 경로 문제 수정. 회귀 검사 추가
2. **PyCG 정답으로 1차 평가** — autojump·asciinema·Fabric에서 세 방법 비교. 전체 F1 향상은 확인하지 못함
3. **기존 PR 반영·병합** — 팀원 PR #4에 수정 커밋을 추가하고 원래 작성자·커밋을 보존해 병합
4. **후속 데이터셋 확보** — Jarvis의 고정 소스·정답·원본 테스트를 확인하고 공통 평가 범위 설정
5. **Jarvis 평가** — sqlparse·furl에서 정확도와 비용 비교. 제한 초과는 미완료로 기록
6. **Jarvis 공개 예측과 비교** — 공개 EA 결과를 같은 앱 함수 범위로 재채점. 재실행·속도 비교와 구분

[PR #4](https://github.com/teamknitcode/knitcode/pull/4) 최종본은 **570 passed, 7 skipped, 41 subtests passed**로 검증했다. 등록된 원격 CI는 없었으며 로컬 main 반영까지 완료했다.

## 3. 데이터와 실험 조건

| 데이터셋 | 프로젝트 | 실행 범위 |
|---|---|---|
| PyCG | autojump | unit: 23 통과·5 skip·4 xfail |
| PyCG | asciinema | config·asciicast: 25 통과 |
| PyCG | Fabric | transfer·group·config: 66 통과 |
| Jarvis | sqlparse | 전체 테스트: 425 통과·3 xfail |
| Jarvis | furl | 75 통과, 기본 실행부터 실패한 2개 제외 |

- 환경: macOS ARM64 / 평가 실행 Python 3.11.8. 프로젝트별 테스트 의존성 고정
- 일반 실행·정상 완료한 추적은 각 3회 반복, 실행 순서 교대. 정적 분석은 1회
- 정밀도는 예측 중 정답 비율, 재현율은 정답 중 발견 비율, F1은 둘을 함께 평가하는 지표
- **분석 총시간 = 정적 분석 + 추적 실행·저장 + 사후 비교.** 추적·비교는 회차별 합의 중앙값 사용
- 일반 실행은 추적 없는 테스트 실행이며, 분석 총시간에 별도로 더하지 않음

## 4. 1차 결과 — PyCG 정답

기존 평가 어댑터의 선택 호출·외부 호출을 포함하는 범위와 공식 채점 함수를 사용했다.

| 프로젝트 | 방법 | 정밀도 | 재현율 | F1 | 분석 총시간 |
|---|---|---:|---:|---:|---:|
| autojump | 정적 단독 | 96.46% | 71.14% | 81.89% | 0.597초 |
| autojump | 정적 + 호출 중심 | 96.46% | 71.14% | 81.89% | 1.303초 |
| autojump | 정적 + 전체 추적 | 96.46% | 71.14% | 81.89% | 1.414초 |
| asciinema | 정적 단독 | 92.06% | 75.07% | 82.70% | 0.320초 |
| asciinema | 정적 + 호출 중심 | 92.06% | 75.07% | 82.70% | 1.120초 |
| asciinema | 정적 + 전체 추적 | 92.06% | 75.07% | 82.70% | 1.277초 |
| Fabric | 정적 단독 | 92.18% | 58.79% | 71.79% | 0.361초 |
| Fabric | 정적 + 호출 중심 | 91.09% | 59.06% | 71.66% | 1.786초 |

autojump·asciinema에서는 연결 가능한 관찰 호출이 이미 정적 결과에 있었다. Fabric은 정답 호출 1개를 보완했지만 정답 밖 관계 3개도 추가돼 F1이 소폭 하락했다. **이 결과만으로 정확도 개선을 주장할 수 없어 후속 데이터셋으로 평가를 확장했다.**

## 5. 후속 결과 — Jarvis 정답

Jarvis GT에는 import·클래스 본문·외부 호출도 포함돼 있다. 이번에는 **소스 AST에서 독립적으로 열거한 앱 함수가 양 끝점인 호출**로 GT와 모든 예측의 범위를 일치시켰다.

- sqlparse: 앱 소스 21파일·3,803줄, 원본 EA 612관계 중 351관계 평가
- furl: 앱 소스 6파일·2,104줄, 원본 EA 319관계 중 189관계 평가

**아래 표는 Jarvis 논문 전체 점수의 재현이 아니다. PyCG 표와 평가 범위가 달라 절대 점수를 직접 비교하지 않고, 각 표 안에서 세 방법의 차이를 비교한다.**

| 프로젝트 | 방법 | 정밀도 | 재현율 | F1 | 분석 총시간 |
|---|---|---:|---:|---:|---:|
| sqlparse | 정적 단독 | 89.52% | 53.56% | 67.02% | 0.550초 |
| sqlparse | 정적 + 호출 중심 | 88.17% | 97.72% | **92.70%** | 6.071초 |
| sqlparse | 정적 + 전체 추적 | 88.17% | 97.72% | **92.70%** | 38.733초 |
| furl | 정적 단독 | 86.46% | 43.92% | 58.25% | 0.329초 |
| furl | 정적 + 호출 중심 | 71.81% | 86.24% | **78.37%** | 65.676초 |
| furl | 정적 + 전체 추적 | — | — | — | 추적 240초 초과 |

| 호출 중심의 보완 효과 | sqlparse | furl |
|---|---:|---:|
| 추가 발견한 정답 관계 | 155개 | 80개 |
| 추가된 GT 밖 관계 | 24개 | 51개 |
| F1 변화 | **+25.68%p** | **+20.12%p** |

sqlparse의 필터 실행에서 실제 선택된 `process` 구현체 등 누락 관계를 보완했다. 두 프로젝트 모두 재현율과 F1은 올랐지만 **정밀도는 내려갔다.** GT 밖 관계는 채점상 FP로 유지했으며, 실제 오류·GT 누락·포함 정책 차이인지는 추가 검토가 필요하다.

## 6. Jarvis 분석기와의 비교

Jarvis가 공개한 `jarvis_EA.json`을 앞선 실험과 **같은 GT·앱 함수 목록·고유 호출 쌍 기준**으로 재채점했다. Jarvis 실행기를 직접 재실행한 결과나 논문 표의 원래 점수는 아니다.

| 프로젝트 | 방법 | 정밀도 | 재현율 | F1 |
|---|---|---:|---:|---:|
| sqlparse | Jarvis 공개 EA 결과 | **99.43%** | 49.57% | 66.16% |
| sqlparse | KnitCode 정적 단독 | 89.52% | 53.56% | 67.02% |
| sqlparse | KnitCode 정적 + 호출 중심 | 88.17% | **97.72%** | **92.70%** |
| furl | Jarvis 공개 EA 결과 | **100.00%** | 50.26% | 66.90% |
| furl | KnitCode 정적 단독 | 86.46% | 43.92% | 58.25% |
| furl | KnitCode 정적 + 호출 중심 | 71.81% | **86.24%** | **78.37%** |

이 범위에서 혼합 방식은 Jarvis 공개 결과보다 sqlparse F1 **26.54%p**, furl F1 **11.46%p** 높았다. 반면 Jarvis는 정밀도가 높아, GT 밖 관계가 적었다.

**현재 주장은 “두 프로젝트의 공통 평가 범위에서 실행 정보를 추가해 더 높은 재현율·F1을 얻었다”까지다.** 순수 정적 분석인 Jarvis와 입력 정보·비용이 다르고, 같은 환경에서 Jarvis 시간·메모리를 측정하지 않았으므로 전반적인 우위나 속도 우위를 주장하지 않는다. 직접 비교를 완성하려면 같은 환경에서 Jarvis를 재실행해야 한다.

## 7. 해석과 다음 단계

**정확도 개선 가능성과 실행 기반 검증의 가치는 확인했다. 모든 프로젝트에서 자동으로 정확도가 좋아지는 것은 아니다.**

- **효과:** 독립된 후속 GT의 두 프로젝트에서 호출 누락과 F1 개선 확인
- **비용:** sqlparse는 같은 점수에서 전체 추적이 더 비쌌고, furl 전체 추적은 240초 제한 초과. 호출 중심도 약 65초 소요
- **검증 기능:** 정적·실행 일치, 실행에서만 발견, 연결 불가를 구분해 사용자가 실행 근거를 검토 가능
- **제품 방향:** 정적 분석을 기본으로 제공하고, 선택한 테스트의 호출 중심 추적을 보조 기능으로 사용
- **다음 작업:** 추가 FP 원인 분류 → 호출 중심 비용 최적화 → 기존 그래프에 실행 근거 표시
- **비교 검증:** Jarvis를 같은 환경에서 재실행해 정확도·전체 비용 비교 보강

결과는 실행한 테스트와 정해진 호출 범위에 한정된다. 미관찰 호출을 오류로 판단하지 않는다. 전체 추적의 분기·변수 정보를 활용하는 보강은 별도 실험이 필요하며, 통계적 유의성이나 대형 프로젝트 전반의 개선은 아직 검증하지 않았다.
